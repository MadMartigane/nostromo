# Nostromo SDK Integration Guide

> Audience: an AI coding agent, or an engineer, building a client library or SDK for a third-party
> app that uses Nostromo as its backend.
> This document is self-contained. It is a contract, not a tutorial: every endpoint, path, field
> name, status code and error message you need is inlined below. You do not need the Nostromo
> repository, and you must not assume it is available.

---

## 1. Purpose and agent rules

**1.1 Read this whole document before writing a single line of integration code.** The behaviors in
section 4 are not optional, and several of them are only meaningful in combination (client-generated
ids plus idempotent creates plus the outbox; the `version` field plus the 409 path).

**1.2 Implement against this contract only.** Do not infer server behavior from the PocketBase
version string, from dashboard screenshots, or from what an older PocketBase release did. Where this
document and your assumptions disagree, this document wins.

**1.3 If the contract seems incomplete, STOP and raise it.** Missing endpoints, ambiguous
authorization, or a requirement that would need a server change are all reasons to stop and ask. Do
not work around the core: do not add proxy shims, do not invent a route, do not relax a check
client-side. A workaround silently breaks the security model, and the security model is the entire
product.

**1.4 NEVER implement rights management client-side.** Groups and access rows are managed by a human
superuser through the PocketBase dashboard. In v1 there is no rights API, no rights UI, and no
"grant access" action a client may perform. A client that thinks it can decide who reads what is
wrong by construction.

**1.5 NEVER route a `/nostromo/*` endpoint through an `/api/` prefix.** Custom routes are registered
at their full path (`/nostromo/invite`, `/nostromo/users/enrich`). The reverse proxy does **not**
strip the prefix. Calling `/api/nostromo/invite` fails. PocketBase's own endpoints, by contrast,
live under `/api/` and are used exactly as documented here.

**1.6 Treat the surface as frozen.** Two custom routes plus standard PocketBase record, auth, file
and realtime endpoints. Nothing else exists. If you find yourself testing an endpoint that is not in
section 3, delete that code.

## 2. Nostromo in one page

Nostromo is a generic multi-app backend built on PocketBase. It is one process, one data directory,
one user pool, shared by several apps; isolation between apps is by user, not by process.

The whole contract is three things:

1. **Authentication** of users.
2. **File storage**: opaque documents, each with an optional attached file.
3. **Access rights**: answering "may user X read or write document Y?"

**The payload is opaque.** Nostromo has zero knowledge of your app's data model. Your documents may
hold your entire state, or one element each; both are valid. The server stores the payload, versions
it, and gates access to it. It never interprets it and never validates its shape.

**Nostromo publishes only the contract, no code.** There is no shared client package, no generated
types, no migration tool. Your app is a pure client and owns its own data model, its own sync engine,
its own outbox, its own merge policy, its own tombstone policy and its own UI.

Two consequences that shape everything below:

- **Document ids are generated by the client.** The server accepts a client-provided id if it
  matches `^[a-z0-9]{15}$`. Local identity is therefore final identity: no id mapping, no
  server-id write-back, no foreign-key rewriting.
- **The server is authoritative for versions.** Each document carries a numeric `version` that only
  the server increments. A write that carries a stale version is rejected with `409`.

## 3. Backend contract

### 3.1 Collections and fields

Exact field names, types and constraints. Use these names verbatim in bodies, filters and code.

**`documents`** (base collection)

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | text (record id) | client-supplied, `^[a-z0-9]{15}$` | required on create |
| `owner` | relation to `users`, max 1 | required | MUST equal the caller's user id on create |
| `payload` | json | none | opaque to the server; JSON object |
| `file` | file, max 1 | max size **20 MiB** (`20971520` bytes) | optional, one file per document |
| `version` | number | required | server-managed; see 3.4 |
| `created` | autodate | set on create | server-assigned |
| `updated` | autodate | set on create and update | server-assigned, display/audit only |

**`groups`** (base collection, superuser-only, never touched by a client)

| Field | Type | Constraints |
|---|---|---|
| `name` | text, max 200 | required, **unique** |
| `members` | relation to `users`, up to 200 selected | optional |
| `created` / `updated` | autodate | server-assigned |

**`document_access`** (base collection, superuser-only, never touched by a client)

| Field | Type | Constraints |
|---|---|---|
| `document` | relation to `documents`, max 1 | required, cascade-deleted with the document |
| `group` | relation to `groups`, max 1 | required, cascade-deleted with the group |
| `right` | select, one of `read` \| `write` | required |

At most one access row per `(document, group)` pair. The pair is unique.

**`users`** (PocketBase auth collection)

- Fields you may rely on: `id`, `email`, `name`, plus PocketBase's `verified`, `created`,
  `updated`. Do not rely on any other user field.
- **Public signup is disabled.** The create rule is unset, so `POST /api/collections/users/records`
  fails for everyone. Accounts are created only through `/nostromo/invite` (section 3.3).
- Self-only rules: a user may list, view, update and delete **only their own** record
  (`id = @request.auth.id`). A client can fetch its own profile and nothing else.

### 3.2 Effective API rules on `documents`

These are the rules the server enforces. They are restated here because your error handling depends
on them, not because you may change them.

Let `caller` be the authenticated user id.

- **list** and **view**: `caller` must be authenticated, and either
  - `owner = caller`, or
  - a `document_access` row on that document has `right` in (`read`, `write`) **and** the row's group
    contains `caller` in `members` (same row semantics: the right and the membership are evaluated on
    one access row, so a `read` row can never grant write).
- **create**: `caller` must be authenticated **and** `owner` in the request body must equal `caller`.
- **update** and **delete**: `owner = caller`, or a `document_access` row with `right = write` whose
  group contains `caller`.

Observable consequences, all verified against a live instance:

- **No access answers `404`, not `403`.** View, update and delete of a document the caller may not
  touch return `404`. Your SDK MUST NOT interpret a `404` on a document it knows about as purely
  "deleted"; it also means "not allowed" or "gone".
- **A filtered list is filtered by rights, not just by the filter.** A list query for a document the
  caller cannot read returns HTTP `200` with `totalItems: 0`. It is not an error.
- **Unauthenticated create answers `400`, not `401`.** The response body is
  `{"message":"Failed to create record."}`. A failed create rule is a validation error in
  PocketBase 0.40.4. The same `400` with that message is returned when an authenticated caller sends
  `owner` different from their own id.
- **`groups` and `document_access` are superuser-only.** Every rule on both collections is unset, so
  any non-superuser list, view, create, update or delete on them is denied. A client never reads or
  writes them.
- **Deleting a document cascades to its `document_access` rows.** Deleting the owner's document
  returns `204` even when access rows exist, and the rows disappear with it.

### 3.3 Endpoints

#### `GET /api/health`

Unauthenticated. Returns `200` when the instance is up. Use it to decide whether to attempt a sync
or to degrade offline. Do not poll it aggressively.

#### `POST /api/collections/users/auth-with-password`

Unauthenticated. Body: `{"identity": "<email>", "password": "<password>"}`.
Success: `200` with a `token` field, plus a `record` object (the user). Cache the token together with
the user id.

Failure: `400` for wrong credentials. Treat any non-`200` as "not authenticated"; never cache a
token from a failed response.

Send the token on every subsequent call as a raw `Authorization` header value:

```
Authorization: <token>
```

That is the form exercised by the acceptance checklist. PocketBase also accepts a `Bearer ` prefix,
but do not depend on it; pick the raw form and stay consistent.

**Graceful offline degradation is required.** When the backend is unreachable, the app MUST stay
usable. Network failure is not an error state for the user; it is a normal state. Queue writes, serve
local data, retry later.

There is no public signup and no self-service password reset in v1. Do not build those screens.

#### `POST /nostromo/invite`

**Superuser only.** No `/api/` prefix. A normal user token is rejected; a missing or invalid token is
rejected. Any non-`200` response means the call is not permitted or not valid, and there is no
recovery path a client should implement: this endpoint is an administrative tool.

Body: `{"email": "<email>", "name": "<optional name>"}`.

- The email is trimmed and lowercased before use. Send lowercase.
- `name` is optional, trimmed, and truncated to 200 characters.
- Email format is validated against a simple pattern. An invalid address returns `400` with the
  message `invalid email: expected a well-formed email address`.

Responses:

| Case | Status | Body |
|---|---|---|
| First invite of this email | `200` | `{"email": "...", "userId": "...", "created": true, "password": "<16-char password>"}` |
| This email was already invited | `200` | `{"email": "...", "userId": "...", "created": false}` (no `password` field) |

Rules you MUST honor:

- **Idempotent on email.** Re-inviting never creates a second account and never returns a password.
  The second response carries the same `userId` and `created: false`.
- **The generated password is returned exactly once.** It is a 16-character alphanumeric string. It
  is never mailed (v1 has no SMTP) and can never be retrieved again. The caller MUST transmit it to
  the user out of band. An SDK MUST surface it immediately and MUST NOT persist it, log it, or
  assume it can be re-fetched.
- **The invite stops at user creation.** It writes no groups and no `document_access` rows. Granting
  access is a separate, manual, superuser operation.
- **Never trigger an invite from client code.** No app screen calls this endpoint. It is invoked
  deliberately by a superuser, outside the app's normal user flow.

#### `POST /nostromo/users/enrich`

**Authenticated** (any user token). No `/api/` prefix.

Body: `{"ids": ["<user id>", ...]}`.

Processing, in this exact order, with these exact rules:

1. `ids` must be an array. Otherwise `400` with `body.ids must be an array of user ids`.
2. Duplicates are collapsed.
3. The caller's own id is removed from the targets.
4. If more than **50** ids remain after steps 2 and 3, the call returns `400` with
   `at most 50 ids per request`. (So a batch of 200 ids containing 150 duplicates and the caller's
   own id may still succeed. Do not pre-validate against 50 too eagerly; the server measures the
   deduplicated, self-removed set.)
5. Each remaining id resolves only if the caller is authorized for that target, meaning **either**
   the caller and target are members of a common group, **or** the target owns a document the caller
   can read (a `document_access` row grants `read` or `write` to a group the caller belongs to).

Response: `200` with `{"users": [{"id": "...", "name": "..."}, ...]}`.

- **`id` and `name` only. Never the email**, never any other field.
- **Unknown ids and unauthorized ids are silently omitted.** The response never reveals whether a
  user exists. An empty `users` array is a valid, successful answer. Do not treat it as an error and
  do not interpret it as "these users do not exist".
- Order is not guaranteed. Match by `id`, not by position.
- `name` may be empty or absent for a user invited without a name. Render a fallback; do not assume
  a non-empty string.

#### `POST /api/collections/documents/records` (create a document)

Authenticated. Body:

```json
{ "id": "a1b2c3d4e5f6g7h", "owner": "<caller user id>", "payload": { "any": "json" } }
```

- `id` MUST be 15 lowercase alphanumeric characters (`^[a-z0-9]{15}$`), generated **by your client**,
  and stable: generate it once, before the first push attempt, and reuse it on every retry.
- `owner` MUST be the authenticated user's own id.
- `payload` is optional and opaque. Send your data as you like.
- Do **not** send `version`; it is server-managed and would be overwritten anyway.

Success: **`200`** (not `201`) with the created record, including `"version": 1` and an echoed `id`.
Every document is born at version 1, superuser creations included.

Failure:

- **`400`** when the id already exists (a repeated create with the same id). Because a `400` is also
  the answer to a broken create rule and to a malformed id, on `400` you MUST re-read the document by
  id before deciding: if it exists and is readable, the create had already succeeded; otherwise
  surface the error as a real failure.
- **`400`** with `{"message":"Failed to create record."}` when unauthenticated, or when `owner` is
  not the caller.
- **`400`** when the id does not match the pattern.

#### `GET /api/collections/documents/records/{id}` (view)

Authenticated. Returns `200` with the record, or `404` when the caller has no read access or the
document does not exist. The two cases are indistinguishable on purpose.

#### `GET /api/collections/documents/records` (list)

Authenticated. This is the **only discovery mechanism for rights**: it returns exactly the documents
the caller may read, and nothing else. There is no rights endpoint, no "shared with me" endpoint, and
no way to enumerate documents you cannot read.

Query parameters worth using (standard PocketBase record listing):

- `page` (1-based), `perPage` (up to 500), and the response envelope
  `{"page":N,"perPage":N,"totalItems":N,"totalPages":N,"items":[...]}`.
- `filter`, `sort`, `fields`. Use `sort=updated` for incremental pulls and `filter=updated>'<ts>'`
  to fetch only changes.
- Filtering happens **after** the rights rule. A filter that matches a document the caller cannot
  read simply yields fewer items; `200` with an empty `items` array is normal.

**The `<ts>` literal MUST use PocketBase's native datetime form, `YYYY-MM-DD HH:MM:SS.SSSZ`**
(space separator, three fractional digits, trailing `Z`), which is exactly the string you find in a
record's `updated` field. Ping-pong the value verbatim: take `updated` from the last record you
received and send it back as the next filter. A working incremental pull:

```bash
# $TS is copied verbatim from the previous response, e.g.
#   2026-09-15 16:49:45.939Z   (URL-encoded: the space becomes %20)
curl -G "$BASE/api/collections/documents/records" \
  -H "Authorization: $TOKEN" \
  --data-urlencode "filter=updated>='$TS'" \
  --data-urlencode 'sort=updated' \
  --data-urlencode 'perPage=500'
```

Use `>=` **and** de-duplicate client-side: several records can share the same `updated`
millisecond, and a strict `>` would silently skip the siblings of the last record you saw.

**The ISO `T` form is rejected by the filter.** `filter=updated>'2026-09-15T16:49:45.939Z'`,
`...T16:49:45Z`, and `...T18:00:00+02:00` all return `200` with `totalItems: 0` (no error, no
match). UTC-offset forms in the native layout (`2026-09-15 18:00:00+02:00`) are not accepted
either. Do not invent a literal: the comparison is a plain text comparison against the stored
timestamp string, so only the server's own format sorts correctly. Verified against PocketBase
0.40.4.

#### `PATCH /api/collections/documents/records/{id}` (update)

Authenticated. Send the fields you intend to change plus the version you expect:

```json
{ "expectedVersion": 2, "payload": { "any": "json" } }
```

- `expectedVersion` MUST be the current numeric `version` of your local copy of that document.
  It may be a JSON number (JSON request) or a string (multipart request); the server coerces it.
- **A missing or non-numeric `expectedVersion` is a stale write**, and is rejected with `409`, not
  `400`. Never omit it.
- Do not send `version`; it is server-managed. Do not send `owner` on updates; ownership transfer is
  not part of this contract.

Success: `200` with the updated record, whose `version` is now the previous version **plus one**.
Store the returned version immediately.

Failure:

- **`409`** with the message `stale write: document version is N`, where `N` is the server's current
  version. This means your copy is out of date. The status is `409` for this case and only this case.
- **`404`** when the caller has no write access (owner or `write`-granted group member), or the
  document is gone.
- **`400`** for a malformed payload.

**404 and 409 mean different things and MUST be handled differently.** `409` is "you have the right,
your data is old". `404` is "you have no right, or the document is gone".

Superusers editing through the dashboard bypass the `expectedVersion` check but still bump `version`,
so a dashboard edit never desynchronizes the version your client holds. It does, however, change the
`version` you must send next time: always take the version from the last server response you saw.

#### `DELETE /api/collections/documents/records/{id}` (delete)

Authenticated. Owner or `write`-granted member. Success: **`204`** with an empty body. The
document's `document_access` rows are deleted with it. A read-only group member gets `404`.

There is **no soft delete on the server**: deletion is permanent, and there is no `deleted` flag.

#### Files

One file per document, optional, max 20 MiB, uploaded through the document record.

Upload with a multipart `PATCH` to `/api/collections/documents/records/{id}`, including
`expectedVersion` **as a string form field** (multipart fields arrive as strings):

```bash
curl -X PATCH \
  -H "Authorization: $TOKEN" \
  -F 'expectedVersion=3' \
  -F 'file=@./photo.jpg' \
  "$BASE/api/collections/documents/records/$DOC_ID"
```

Success: `200` with the record, whose `file` field holds the stored filename. The upload bumps
`version` like any other update, and the same `409` semantics apply.

A file part larger than 20 MiB (`20971520` bytes) is rejected with `400` and a body carrying
`data.file.code` `validation_file_size_limit` (message `Failed to upload <name> - the maximum
allowed file size is 20971520 bytes.`). The record is left unchanged.

Download: **a document file is a protected resource, not a capability URL.**

The `file` field is **protected**. A download therefore requires a short-lived **file token** in
addition to (and on a different request than) the user's auth token:

```
POST /api/files/token                  # Authorization: <the caller's user token>, empty body
GET  /api/files/documents/{documentId}/{filename}?token={fileToken}
```

`POST /api/files/token` returns `200` with `{"token": "<file token>"}`. The response carries no
duration field; the returned token is a JWT whose `exp` claim was exactly **180 seconds** ahead of
issuance when measured against PocketBase 0.40.4, so treat it as short-lived (minutes, not hours)
and never cache it long-term.

Rules the download MUST satisfy:

- **The file token travels in the query string** as `?token=...`. It is not sent as a header.
- **A plain `Authorization` header is NOT sufficient.** `GET .../file` carrying the caller's user
  token as an `Authorization` header, with no `?token=`, returns `404`. There is no header-based
  fallback; do not build one.
- **An anonymous `GET` with no token returns `404`.** With a valid file token in `?token=` no header
  is needed: the token-bearing URL is a bearer capability for the token's short lifetime (see 4.9).
  A token issued to a caller who does not satisfy the viewRule still returns `404`.
- **Access is view-rule based, not token based.** Any caller who satisfies the `documents` viewRule
  receives the file: the record's owner, or a group-granted reader (a `document_access` row granting
  `read` or `write` to a group that contains the caller). File access and record access are the same
  check, so a group grant needs no extra step. Verified live: a group-granted reader's own file token
  returns `200` with byte-identical content.
- **A valid file token never bypasses a failing viewRule.** A caller with no read access gets `404`
  even with a freshly minted token of their own. The token proves *who* is asking; the viewRule
  decides *whether* they may read.
- **The token is a bearer capability for its lifetime.** Although only a caller with read access can
  obtain one, anyone holding the resulting token-bearing URL can fetch the bytes for the token's
  short life. Do not log it, do not persist it, and do not fetch file URLs over plain HTTP.
- **Fetch a fresh file token per download.** A token must be obtained with the current user's auth
  token and used promptly; never reuse another user's token, and never assume a stored one is still
  valid.
- **Filenames are chosen by the client.** The server derives the stored name from the name you send
  plus a random suffix. Never rely on name obscurity for security.
- **A missing filename (or a document you may not read) returns `404`.**

Verify the download against the upload byte for byte; the server does not transform the file.
(Verified against PocketBase 0.40.4: an anonymous request with no token returned `404`; the owner's
token download, a group-granted reader's token download, and an anonymous request holding a valid
token with no header all returned `200` with content identical to the uploaded bytes; a plain
`Authorization` header without `?token=` returned `404`; a valid token issued to a caller with no
read access returned `404`.)

#### Realtime

Subscribe to the `documents` collection and re-pull on change events. The official PocketBase SDKs
expose this as a subscribe call over the standard realtime transport; the underlying topic is the
collection name `documents`. Treat realtime as an optimization and a latency improvement, never as
the source of truth: the source of truth is the record returned by a pull. If the realtime
connection drops, your sync loop must still converge through periodic listing.

### 3.4 Versioning, precisely

- The conflict token is the numeric **`version`** field. It is server-managed and incremented by
  exactly one on every accepted write.
- **`updated` is NOT the conflict token.** It is display and audit data only. Never send it as a
  conflict token, never compare it to detect staleness, never use it as an `if-match` value.
- A document is created at `version` 1.
- A create with an explicit `version` in the body still lands at 1; the server sets it.
- A successful update returns the new version; the client stores it.
- A stale update is rejected with `409` and the document is left unchanged.
- A superuser dashboard edit skips the check but still bumps the version.

### 3.5 Error semantics summary

| Status | Meaning | Client action |
|---|---|---|
| `200` | success (also for create and update) | store the returned record, including `version` |
| `204` | delete succeeded | remove locally, cascade to any local access metadata |
| `400` | validation: bad id, duplicate create, failed create rule, malformed body, bad email, bad `ids` | on create, re-read the document by id to distinguish "already exists" from a real error; otherwise surface it |
| `401` | authentication problem on an auth-only endpoint | re-authenticate |
| `404` | no access, or the document is gone (indistinguishable) | never conclude "deleted" from this alone; re-list to decide |
| `409` | **stale write only** | take the mandatory conflict path (section 4.3) |
| `5xx` / network failure | server unavailable | degrade offline, retry with backoff, keep local data intact |

Never retry a `400`, a `404` or a `409` unchanged: those are deterministic answers. Retry `5xx` and
network failures with backoff.

## 4. Required SDK behaviors

These are requirements on your library. Each one is testable, and each one exists because omitting
it breaks data or security.

### 4.1 Client-generated ids

Generate document ids locally, 15 lowercase alphanumeric characters (`^[a-z0-9]{15}$`), before the
first push. An id is part of the document's identity forever; it is never rewritten after a create.
This makes creates idempotent and removes the need for an id map, server-id write-back, or
foreign-key rewriting.

### 4.2 Per-document version tracking

Track the numeric `version` per document, updated from **every** server response that carries the
document (create, update, list item, view, file upload). The conflict token you send is `version`.
Never `updated`.

### 4.3 One mandatory rejection path for `409`

Give your SDK exactly one code path for a stale write, and make it mandatory. On `409` you MUST do
one of:

1. re-pull the document, re-apply the local change on top of the fresh state, and retry with the new
   version, or
2. surface a conflict to the application/user, or
3. park the write and let the app resolve it.

**Last-write-wins survives only as the automatic merge rule when no rejection is involved.** It is
not a license to ignore a `409`. Silently discarding a `409`, or retrying with the corrected version
without re-applying the local change, is forbidden: the second form would overwrite a concurrent
change with stale data.

### 4.4 Outbox keyed by document id

Keep a persistent outbox with at most one pending write per document id. Retries are safe because
creates are idempotent and updates carry an explicit `expectedVersion`. Bound the outbox, persist it
across restarts, and drain it in the order the app's own payload graph requires (the core imposes no
order).

### 4.5 Realtime-driven pulls

Subscribe to `documents` and re-pull the changed record on each event. Keep a periodic full or
delta list as a fallback so a dropped realtime connection cannot silently stop synchronization.

### 4.6 Offline-first

The app MUST remain usable when the backend is unreachable. Reads come from local storage; writes go
to the outbox; authentication failure or timeout MUST NOT block the UI. Sync resumes when
connectivity returns.

### 4.7 Tombstones and first sync are app-side

- The core has **no deleted flag**. If your app wants soft deletes, it stores its own tombstone
  documents in the payload. Design that yourself.
- The first-sync policy (merge, adopt-remote, or ask the user) is app-side. The core gives you a
  list and gets out of the way.
- Deletion on the server is permanent and cascades to access rows. A locally known document that
  returns `404`, or that vanishes from a list, is either deleted or no longer readable; treat both
  as "no longer synchronizable" and let the app decide what to keep.

### 4.8 Robustness rules

- Never store, log or transmit a user's password after the initial invite handoff.
- Never log tokens or payloads of other users.
- Batch enrich calls: at most 50 deduplicated ids, and never include the caller's own id.
- Do not build a "search users" screen on enrich. It answers about specific ids, and it deliberately
  leaks nothing about ids the caller may not see.
- Do not assume a `200` means "the document still exists" for a list: an empty list is a normal
  answer.

### 4.9 Protected file downloads

Document files are **protected**. A download is two calls, not one:

1. `POST /api/files/token` with the current user's `Authorization` header (empty body) returns
   `{"token": "<file token>"}`.
2. `GET /api/files/documents/{documentId}/{filename}?token=<file token>` returns the bytes.

Requirements:

- Send the file token as the `?token=` query parameter. A plain `Authorization` header on the file
  URL is **not** sufficient and returns `404`; do not build a header-based fallback.
- The token is **short-lived** (180 seconds observed on PocketBase 0.40.4). Fetch a fresh token for
  each download, never cache one beyond its life, and never log or persist it.
- A file token never grants access by itself: the server still applies the `documents` viewRule, so
  a valid token issued to a caller without read access returns `404`. An anonymous request with no
  token also returns `404`; with a valid token in `?token=` and no header it succeeds, because the
  token-bearing URL is a bearer capability for the token's lifetime. Never treat a stored file URL as
  capability: it carries access only with a valid, current token.

## 5. Prohibited

1. **Never call `/nostromo/*` through an `/api/` prefix.** The proxy does not strip prefixes, and
   custom routes are registered at their full path. `/nostromo/invite` is correct;
   `/api/nostromo/invite` does not exist.
2. **Never trigger an invite from client code.** Invite is superuser-only and deliberate. Apps do
   not create accounts.
3. **Never manage rights client-side.** No UI, no API call, no local computation of who may read
   what. The listing call is the only rights discovery mechanism: if a document is not in the list,
   the app cannot read it.
4. **Never assume an app schema on the server.** The payload is opaque; the server has no app
   collections, no app fields, and no junction tables for your model. Membership, teams, clubs and
   everything else live in payloads.
5. **Never depend on a server behavior not stated here.** If you need one, stop and raise it.

## 6. SDK landscape

**Pin: PocketBase server 0.40.x. PocketBase is PRE-1.0 and any 0.x release may introduce breaking
changes without a deprecation period. Nostromo itself makes no backward-compatibility guarantee
across PocketBase minor versions.** Write your integration so that the version you were tested
against is recorded and asserted, and treat a server upgrade as a change that must be re-validated
against the acceptance checklist in section 7.

Recommended clients:

| Stack | Recommendation |
|---|---|
| JavaScript / TypeScript | Official SDK `pocketbase` (npm), the 0.27.x line. Covers auth, records, files and realtime. For stronger typing, `typed-pocketbase` wraps it. |
| Dart / Flutter | Official SDK `pocketbase` (pub.dev), the 0.25.x line. |
| Python | Community client `vaphes/pocketbase` is usable, or use a plain HTTP client. |
| Rust | The available SDKs are stale. Use a plain HTTP client against the documented endpoints. |
| Anything else | Use a plain HTTP client. Every endpoint, field and status code you need is in this document. |

Rules that apply regardless of the client:

- Verify that your SDK version targets the pinned PocketBase 0.40.x line before relying on it.
- **Never rely on an SDK feature that is not in this contract** (no auto-cancellation semantics, no
  offline layer, no built-in sync, no admin API helpers). If an SDK offers one, treat it as
  unavailable.
- Whatever the client, your integration MUST pass the acceptance checklist in section 7 against the
  real server.

Example (official JS SDK), showing the pieces that matter:

```js
import PocketBase from 'pocketbase'

const pb = new PocketBase('https://app.example.com') // same origin as the app, no /nostromo here

await pb.collection('users').authWithPassword(email, password)

// create with a client-generated id
const id = generateId15() // ^[a-z0-9]{15}$
const doc = await pb.collection('documents').create({
  id,
  owner: pb.authStore.model.id,
  payload: { any: 'json' },
})
// doc.version === 1

// update, sending the version we hold
try {
  const updated = await pb.collection('documents').update(id, {
    expectedVersion: doc.version,
    payload: { any: 'json', rev: 2 },
  })
  // updated.version === 2
} catch (err) {
  if (err.status === 409) {
    // mandatory conflict path: re-pull, re-apply, or surface it
  } else if (err.status === 404) {
    // no write access, or the document is gone
  }
}

// realtime: re-pull on change, never treat the event as the source of truth
await pb.collection('documents').subscribe('*', async (e) => {
  const fresh = await pb.collection('documents').getOne(e.record.id).catch(() => null)
  if (fresh) applyRemote(fresh)
})
```

The custom routes are plain HTTP; call them with `fetch` or your HTTP client of choice
(`POST /nostromo/invite`, `POST /nostromo/users/enrich`).

## 7. Acceptance checklist

Every item is a testable behavior, numbered to match the project's end-to-end contract check. An
implementation is not integration-complete until all 27 pass against the real server, plus the three
supplementary checks in section 7.1 (marked **beyond smoke.sh coverage**). `TOKEN` means the raw
`Authorization` header value.

### Health

1. `GET /api/health` returns `200`. If not, abort the run: the instance is unreachable.

### Authentication

2. `POST /api/collections/_superusers/auth-with-password` with `{"identity": <superuser email>,
   "password": <superuser password>}` returns `200` and a non-empty `token`.
3. `POST /nostromo/invite` with the superuser `Authorization` header and body `{"email": <new>,
   "name": <name>}` returns `200` with a non-empty `userId`, `created: true`, and a non-empty
   `password`.
4. A second `POST /nostromo/invite` with the same email returns `200` with the **same** `userId`,
   `created: false`, and **no** `password`.
5. `POST /api/collections/users/auth-with-password` with that email and the invited password returns
   `200` and a non-empty `token`.
8. Invite a second user and authenticate them: invite returns `200` with `created: true` and a
   password, auth returns `200` with a token.

### Documents: create and access

6. `POST /api/collections/documents/records` as the first user, with a client-generated 15-char id,
   `owner` equal to the caller's id, and a payload, returns `200`, echoes the same `id`, sets
   `owner`, and reports `version` `1`.
7. A second create with the **same id** returns `400`.
24. `POST /api/collections/documents/records` with no `Authorization` header returns `400` with
   message `Failed to create record.`
9. The second user's `GET /api/collections/documents/records/{id}` on the first user's document
   returns `404`.
10. The second user's list query filtered on that document id returns `200` with `totalItems: 0`.

### Rights and writes

11. A superuser creates a `groups` record (name plus the second user in `members`) and a
    `document_access` record `{document, group, right: "read"}`; both creations return `200` with
    non-empty ids. (Superuser flow only: a client never performs this.)
12. After that grant, the second user's `GET` of the document returns `200` with `version` `1`.
13. The second user's `PATCH` with `{"expectedVersion": 1, "payload": {...}}` returns `404`
    (read-only: read access does not permit writes).
14. The owner's `PATCH` with `{"expectedVersion": 1, "payload": {...}}` returns `200` and
    `version` `2`.
15. The owner repeats the same `PATCH` with `{"expectedVersion": 1, ...}` and gets `409`.
16. A superuser flips the access row to `right: "write"` (`200`); the second user's `PATCH` with
    `{"expectedVersion": 2, ...}` then returns `200` and `version` `3`.
25. With the access row back at `right: "read"`, the second user's `DELETE` of the document returns
    `404`.

### Files

17. The owner uploads a file with a multipart `PATCH` carrying `expectedVersion` as a **string**
    form field and the file part; the response is `200` and the record's `file` field is non-empty.
18. The owner obtains a file token with `POST /api/files/token` (the user's `Authorization`
    header, empty body), which returns `200` with a non-empty `token`; `GET
    /api/files/documents/{id}/{filename}?token={fileToken}` then returns `200` and the bytes are
    identical to the uploaded file. (A plain `Authorization` header, with no `?token=`, returns
    `404`: the header alone is not sufficient, see 3.3 Files.)
19. The second user, once a group-granted reader (check 16), obtains **his own** file token with
    `POST /api/files/token` and downloads the owner's file with `?token={hisToken}`: `200` and bytes
    identical to the upload. File access is view-rule based, not owner based.
20. A third user, invited and authenticated but sharing no group and no access row with the
    document, obtains **her own** valid file token and sends it as `?token=` on the owner's file
    URL: `404`. A valid token proves who is asking; the viewRule decides whether they may read.
21. An anonymous `GET` of that same file URL, with no token and no header, returns `404`. This is
    the regression guard for file protection: before the `file` field was protected the same
    request returned `200`. (An anonymous `GET` **with** a valid token in `?token=` succeeds, see
    3.3 Files: the token-bearing URL is a bearer capability for the token's lifetime.)

### Users enrichment

22. `POST /nostromo/users/enrich` as the second user with `{"ids": [<first user's id>]}` returns
    `200` and `users[0]` is that id with that user's `name`. (The two users do not share a group
    here: the authorization comes from the second clause, the target owns a document the caller can
    read.)
23. `POST /nostromo/users/enrich` with `{"ids": [<an unrelated 15-char id>]}` returns `200` and an
    empty `users` array.

### Deletion

26. The owner's `DELETE` of the document, while an access row still exists, returns `204`.
27. After that delete, `GET` by the owner returns `404`, `GET` by the group member returns `404`, and
    a superuser list query on the `document_access` row id returns `200` with `totalItems: 0`: the
    access row cascaded with the document.

### 7.1 Supplementary checks (beyond smoke.sh coverage)

These three cases are **beyond smoke.sh coverage**: they are not exercised by the project's scripted
end-to-end check, so keep the 1:1 mapping between items 1-27 and smoke.sh. Run them by hand. Expected
statuses verified live against PocketBase 0.40.4.

Anonymous file download is **not** listed here: with the `file` field protected it returns `404`, and
that expectation is core-covered by item 21 (smoke check 21).

S1. `POST /nostromo/invite` with **no** `Authorization` header returns `401` with body
    `{"data":{},"message":"The request requires valid record authorization token.","status":401}`.
    **Beyond smoke.sh coverage.**
S2. `POST /nostromo/users/enrich` with **no** `Authorization` header returns `401` with the same
    body as S1. **Beyond smoke.sh coverage.**
S3. Uploading a file larger than 20 MiB (e.g. 21 MiB) with a multipart `PATCH` carrying
    `expectedVersion` returns `400`, with body `data.file.code` `validation_file_size_limit` and
    message `Failed to upload <name> - the maximum allowed file size is 20971520 bytes.` The record
    is left unchanged. **Beyond smoke.sh coverage.**
